# Valar 跨框架组件转换规范

规范版本：1.0 · 生效日期：2026-10-31

本规范适用于 Valar 系列中 React、Vue、Svelte 等框架之间任意方向的组件转换，包括基础组件、组合组件、业务区块，以及更换底层交互库。AI 与人工贡献者遵循同一套要求。

目标是以目标框架的原生方式实现约定的能力、状态和交互，并保持 Valar 的设计语言。截图相似、属性同名、编译通过或页面没有报错，都不能单独证明转换完成。

“必须”表示完成条件；“建议”允许按实际情况选择。用户明确指定的范围和设计变更优先，必须在记录中写明依据及影响。不要把用户有意要求的差异当作缺陷，也不要以“简化实现”为由悄悄删减能力。

## 1. 开始前：明确来源、范围和版本

执行者必须先完成以下工作，再开始实现：

1. 阅读目标仓库的 `AGENTS.md`、本规范，以及源组件的实际实现、直接依赖和相关测试。截图只能作为视觉参考，不能代替源码和行为分析。
2. 记录来源仓库、文件路径、提交 SHA 或发布版本、许可证；记录目标框架、运行环境和相关依赖版本。涉及具体 API 时查阅对应版本的官方文档，不凭名称推测兼容性。
3. 检查目标库是否已有等价组件、不同名称的实现、可组合的原语或废弃组件的替代方案，避免重复引入。
4. 定义本次需要保留的能力、Valar 有意调整的行为、是否允许修改样式，以及支持环境。组件转换本身不授权更改最低兼容版本、业务规则或发布配置。
5. 核对源码和新增依赖的许可，保留必要的版权与许可说明；品牌独立化不等于删除来源义务。
6. 复制[转换记录模板](templates/COMPONENT_PORTING_RECORD.md)到 `standards/porting-records/<component>-<source>-to-<target>.md`，先填写分析，再随实现补充证据。一组组件可共享背景，但每个独立组件都要有明确的能力与验收结果。

已有用户指令足以决定范围时直接执行，不为常规实现选择反复索取确认。遇到无法推断的关键产品取舍时，提出具体问题，同时继续不受影响的工作。

## 2. 先定义能力合同，再转换代码

每个组件必须建立“来源能力 → 目标行为 → 实现方式 → 差异及影响 → 验证证据”对照表，至少说明：

- 结构、输入属性、输出事件、默认值、必需和可选能力。
- 状态归属、受控与非受控用法、外部更新、绑定方式、事件载荷及触发时机。
- 键盘、鼠标、触摸、焦点、表单和无障碍行为。
- 异步、生命周期、服务端渲染、主题和布局约束。

有交互状态的组件还须描述状态转换。例如“空闲 → 校验中 → 有效／无效 → 下一步”，并覆盖取消、回退、重复操作和过期异步结果。视觉上的同一个状态不代表内部的数据状态相同。

跨框架共享的是用户可观察的能力和行为合同，不强求所有属性、事件、插槽或文件结构完全同名。React 的 children/hooks、Vue 的 slots/emits/v-model、Svelte 的 snippets/runes/bindings 应采用所选版本的原生惯例；映射与差异必须可查。

## 3. 实现规则

- 优先使用经过核验的目标框架原生交互原语。源组件依赖的 React/Vue/Svelte 库不能假定可直接复用；替代库即使组件同名，也要核对行为。
- 不默认嵌入另一框架的运行时，也不为一个组件复制整套库。确需桥接时，记录体积、生命周期、SSR、样式、维护成本和选择理由。
- 明确单一数据源、派生值和副作用的边界，避免双向同步循环、过期闭包、重复事件及内部状态覆盖外部更新。
- 正确转发属性、事件、class、ARIA 属性和元素引用；核对组合子组件、插槽内容和自定义触发器的行为。
- 清理计时器、监听器、观察器和请求，防止卸载后写入、资源泄漏及旧请求覆盖新结果。
- 使用 Valar 的语义 token。为适配原语可以调整 DOM，但必须重新核对选择器、布局、焦点和状态样式；不能借转换擅自改变已约定的视觉方向。
- 无法等价实现的能力必须显式标注。禁止以空函数、无效属性、静态假状态或隐藏异常冒充支持。

## 4. 必须逐项判断的验证范围

每一行都必须在转换记录中标记“适用”或“不适用及原因”。验证深度按风险决定：静态展示组件不必执行复杂输入控件的全套测试，但不能因验证困难而把适用项目记为不适用。

| 维度 | 必须考虑的场景 |
| --- | --- |
| 状态与数据 | 默认值、受控／非受控、外部更新、空值、边界、禁用、只读、事件次数与顺序；明确是否支持运行中切换控制模式 |
| 表单语义 | name/value、提交、重置、required、invalid、禁用字段的提交行为、错误关联；显示文本与提交值是否一致或有明确转换 |
| 键盘与焦点 | Tab/Shift+Tab、Enter、Space、Escape、方向键、Home/End 等适用按键；可见焦点、进入与退出、关闭后恢复、嵌套交互 |
| 无障碍 | 原生语义优先、角色、可访问名称、状态和描述关联、错误与动态变化的播报；自动扫描不能代替键盘和必要的辅助技术验证 |
| 输入法与国际化 | 中文等输入法组合输入，Enter 确认、粘贴、删除、选区、Unicode、地区格式、长文本；RTL 下的布局及方向键规则 |
| 触摸与指针 | 点击、拖动与取消、页面滚动冲突、软键盘、触控区域；不能仅靠 hover 暴露必要能力 |
| 异步与生命周期 | 加载、失败、重试、重复提交、取消、竞态、卸载及重新挂载；等待和失败期间的焦点与可操作性 |
| SSR 与 hydration | 模块加载时的浏览器 API、稳定 ID、首屏状态一致性、地区／时区／随机值差异、闪烁和 hydration 警告 |
| 弹层与布局 | Portal 容器、层级、裁剪、滚动锁定、定位、嵌套弹层和容器内使用 |
| 视觉与适配 | 浅色／深色、所有交互状态、尺寸、缩放、响应式、长文本、对比度和减少动态效果偏好 |
| 性能与资源 | 大列表、频繁输入、不必要更新、清理、包体变化；如使用虚拟化，核对焦点和无障碍语义 |
| 安全与隐私 | 涉及 HTML／代码渲染、链接、剪贴板、上传、外部请求时的输入边界；不附带无关统计或数据外传 |
| 类型与依赖 | 公共类型、泛型、事件类型、导出、peer dependency 和版本；不能用宽泛 any 或忽略检查掩盖契约不匹配 |
| 分发与集成 | registry 文件及依赖闭包、路径别名、样式依赖、公共导出；脱离 monorepo 的消费者能否按文档安装并使用 |

环境或工具不可用时，记录“未验证”、影响与下一步，不得写“通过”。静态检查、单元测试、浏览器测试、人工验证各自只能证明其实际覆盖的部分。

## 5. 典型组件的易遗漏行为

以下是检查示例，不代替来源分析，也不要求所有组件提供相同功能。最终范围以能力合同为准。

### Number Field

区分编辑中的字符串与提交后的数值；空值、负号 `-`、小数输入中的 `1.` 等中间状态不能被无意吞掉或强制变成 0。核对精度、min/max/step、负数、地区格式、粘贴、步进按键和表单提交，并明确何时规范化：输入、失焦、提交还是步进时。

### Tags Input

区分输入文本、候选项和已选标签；输入法确认不能误触发添加。核对空标签、重复、数量限制、分隔符、删除键、删除后的焦点、只读／禁用和序列化后的表单值。

### Stepper

区分当前、完成、错误和不可到达的步骤；核对线性／自由跳转、异步校验、连续点击、回退后的数据保留、动态增减步骤和焦点转移。步骤与内容必须有恰当的语义关联，不能用进度条外观替代流程行为。

### Dialog、Popover、Select

核对打开／关闭、Escape、外部点击、关闭后的焦点恢复、嵌套和 Portal。焦点限制、模态语义及键盘规则取决于具体组件模式，不能把所有弹层都当作模态对话框。

## 6. 完成标准与证据

转换只有满足已约定范围内的全部必要条件，才能标记为“完成”：

1. 能力对照表已填写，所有保留能力有实现和验证证据；有意差异注明依据、影响及使用方式。
2. 按改动范围执行类型检查、构建和必要的行为回归。测试验证对外行为和边界，不只复述实现代码；关键交互变化应留下可重复的回归验证。
3. 第 4 节每个维度均完成适用性判断；所有适用且必要的项目有实际结果。键盘、输入法、焦点、表单等交互不能仅凭截图验收。
4. 按支持范围检查浅色／深色、响应式、边界状态，以及适用的 SSR/hydration。复杂组件增加真实组合场景，例如弹层中的表单。
5. 可分发组件必须通过实际分发路径（registry、本地包或 tarball）在独立消费者工程中安装，验证公共导入、类型、样式、直接／传递依赖和代表性交互。不以仓库内示例能运行代替此项，不依赖未声明的 monorepo 路径或依赖。
6. 示例、文档、registry 与公开 API 一致；交付必要的来源和许可说明。
7. 转换记录包含实际环境、命令、结果和可定位的测试／产物／人工步骤，不写入敏感信息。失败、未运行、未验证必须如实记录。

“部分实现”“待验证”与“完成”必须区分。只要约定范围内仍有未实现能力或必要验证缺口，就不能宣称完整转换。用户明确接受缩小范围时，记录原始范围、排除项、依据和影响，按最终范围验收，不伪造等价性。

最终交付说明应回答：转换了什么、行为差异是什么、如何验证、哪些仍有限制，以及对应转换记录在哪里。未要求发布时，不把提交、推送、npm 发布或网站部署作为验收前提。

## 7. 后续维护与不同 AI 的接入

- 保留来源版本与差异记录。更新上游或替换依赖时重查受影响的能力合同，运行关键回归，保留 Valar 有意定制。
- 本文件是规范正文；`AGENTS.md` 和 `CONTRIBUTING.md` 只维护入口，避免多份正文冲突。修订正文时更新版本，并在后续转换记录中引用实际采用的版本。
- 未来建立 Valar React、Valar Vue 或其他框架仓库时，应同步这套规范、模板及 `AGENTS.md` 入口，记录来源与版本。当前文档不代表这些仓库已经建立或完成同步。
- `AGENTS.md` 是仓库入口，不保证所有 AI 工具自动读取。使用不自动加载它的工具时，必须在任务上下文中显式提供入口、规范和记录模板；不能只传一张截图。
- 本规范目前通过任务要求和交付审阅执行，不宣称已配置 CI 自动门禁。自动检查可辅助验证文件与测试结果，不能独自证明语义等价。

可复用任务说明：

> 将【来源组件及固定版本】转换为【目标框架及版本】的 Valar 组件。开始前阅读仓库 AGENTS.md、standards/COMPONENT_PORTING.md 和转换记录模板；先建立能力对照与状态模型，再使用目标框架原生方式实现。逐项考虑键盘、焦点、输入法、表单、无障碍、SSR、主题和实际分发。填写转换记录并提供可重复的验证证据；未实现或未验证项如实标记，不得以外观相似或编译通过宣称完成。
